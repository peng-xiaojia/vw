---

## 1. 一句话规则

> **读它，不 fork 它；移植工程资产，不移植领域代码。**

---

## 2. 为什么需要这份文档

dbx 是一个源码约 65 MB、百万行量级、当日仍在提交的活跃项目。把这样一个项目当作「参考」，如果没有明确规则，会滑向三种失败模式：

| 失败模式 | 表现 | 代价 |
| --- | --- | --- |
| 滑向 fork | 开始删减它的代码，工作量花在「识别边界并删除」上 | 删减不产生价值，且继承了它的领域假设 |
| 滑向领域污染 | 把数据库的抽象（连接、查询、结果集）带进文件查看器 | 内核不再零格式知识，架构统一性被破坏 |
| 滑向追随 | 为了跟上上游而付出成本 | 我们从来不是它的 fork，跟随毫无收益 |

不 fork 整体的完整理由与实测数据见设计规格 §3.1。本文档给出的是**可执行的边界**。

---

## 3. 三条规则

### R1 读而不 fork

- **不**把 dbx 的仓库 clone 到本项目工作区，**不**将其作为 git remote。
- **不**整目录复制其代码。任何复制都必须逐条记录（见 §6）。
- 允许的做法：按需用 `git clone --depth 1` 克隆到**工作区之外**的临时目录用于阅读，读完即弃。工作区内不留下它的工作树。

### R2 移植必须过判据

任何一段想搬过来的代码，先过 §5 的五道判据。**任一为否，就重写。**

### R3 领域代码零移植

数据库、连接、SQL、游标、schema、事务、凭据加密、消息队列控制台、AI 助手、Web/Docker 后端——**一律不移植，甚至不必精读**。这些恰好是本项目不需要的 97%。

## 5. 移植判据

对每一段候选代码，逐条回答。**任一条为「否」，就重写，不移植。**

1. **它和数据库领域无关吗？** 涉及连接、查询、结果集、schema、凭据的，直接否决。
2. **剥掉 dbx 的业务概念后，它还剩下多少？** 若一百行里九成是业务，剩下一成不值得抄。
3. **它的抽象与我们的契约兼容吗？** 我们只有 `Source`、`Viewer`、`Doc`、`EditableDoc`、`Document IR`。若需要为它改造这些契约来适配，就否决。
4. **它引入的依赖我们能接受吗？** 对照设计规格 §14.1 的选型。任何会把 `vw-core` 拉重的依赖都否决。
5. **我们能在 30 分钟内给它写出测试吗？** 写不出，说明这段代码的边界不清晰，抄过来也是负担。

## 6. 合规要求（Apache-2.0）

Apache-2.0 允许复制与修改，但有明确义务。**任何移植都必须完成以下四项：**

1. **保留许可与声明。** 在本仓库根目录保留 dbx 的 `LICENSE` 副本，并以 `NOTICE` 形式保留其声明。
2. **标注修改。** 移植的文件在文件头注明来源，格式固定为：

   ```
   // 源自 t8y2/dbx @ 051cab8 <原文件路径>
   // Apache-2.0。本地修改：<一句话说明改了什么>
   ```

3. **登记台账。** 在 [`docs/THIRD-PARTY-NOTICES.md`](../THIRD-PARTY-NOTICES.md) 逐条登记：来源仓库、锚点 commit、原文件路径、目标文件路径、修改摘要。
4. **不搬运品牌。** 不使用 dbx 的名称、图标、商标用于本项目的命名或宣传。命名上必须与本项目无关。

**注意**：只借鉴**设计思想与接口形态**（例如「manifest 里用权限串声明能力」这种思路）不构成复制，无需署名；但**逐字照搬代码**必须完成上述四项。判断不清时，按「需要署名」处理。

## 7. 版本锚定

- 本文件顶部的**参考锚点**是唯一的阅读基准。阅读与移植时一律 `git checkout 051cab8`，**不要读 `main` 的最新状态**——否则你在参考一个移动的目标。
- 每个大阶段（P1/P2/…）开始时，评估是否需要更新锚点：
  - 更新时在本文件记录新锚点，并写一句「为什么更新」。
  - 已移植的代码**不因上游更新而跟改**，除非上游修的是影响我们的安全缺陷。
- 记录格式（追加到本节末尾，最新在上）：

| 锚点 | 日期 | 更新原因 |
| --- | --- | --- |
| `051cab8` | 2026-10-13 | 初始锚点 |

## 8. 红线

以下任一情况出现，立即停下并重新评估：

| 红线 | 说明 |
| --- | --- |
| 工作区里出现 dbx 的工作树 | 说明已经滑向 fork（R1） |
| 为了兼容 dbx 的结构而修改本项目的契约 | 说明领域污染已经发生（R3） |
| 在讨论「如何跟上 dbx 的更新」 | 我们不是它的 fork，这个问题本身不成立 |
| 发现自己正在重写 dbx 的某个完整模块 | 停下来问：这个能力真的需要自研吗？能否直接依赖上游库？ |
| 未登记的移植代码 | 违反 §6，属许可风险 |

---

## 9. 定期复评

每个阶段（P1–P5）结束时回答两个问题：

1. **dbx 是否出现了值得重读的新东西？** 若有，更新锚点并记录。
2. **我们的设计与 dbx 是否出现了同构？** 这可能是正确的技术收敛，也可能是领域污染。判据很简单：**看我们是否因此引入了数据库领域的概念**。引入即污染，没有则视为收敛。
