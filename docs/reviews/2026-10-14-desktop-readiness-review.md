# vw 桌面交付审查与整改方案

审查日期：2026-10-14。代码基线：`f9e21c2`。本轮仅审查，未修改功能代码、系统文件关联或发布配置。

后续已实施桌面整改。本文保留原始审查证据；当前功能与本机验证见 [桌面能力矩阵](../desktop-capabilities.md) 和 [开发收尾验证](2026-10-14-desktop-completion-validation.md)。正式签名及干净 Windows 系统验收仍未完成。

## 结论

当前项目具备可复用的插件内核、统一文档模型和三个外壳，但 GUI 仍是以手输路径为入口的初步实现，Windows 安装与系统集成尚未完成。不能把「底层接口存在、命令层测试存在」作为「桌面产品交付完成」的依据。

建议保留现有架构，补齐 GUI 文档状态管理、浏览工作区和 Windows 发布工程。应先修复数据丢失、错误保存语义和不可信链接，再补用户入口与系统集成。

## 审查范围与证据边界

检查了设计规格、README、Tauri 入口与配置、GUI 命令层和前端、目录插件、文本编辑模型、归档会话与保存路径、标准插件装配、sidecar 启动代码和相关测试。

- 对当前 `target/debug/vw-app.exe` 读取 PE 头并检查 Authenticode 签名。
- 使用 Node 执行实际前端代码，配合最小 DOM 和 IPC 替身，复现状态切换及分页问题。这不是原生 WebView 端到端测试。
- 使用实际 Rust 编译产物运行只针对测试夹具的探针，验证文本缓存和 ZIP 成员保存语义。
- 执行相关 Cargo 测试；失败如实记录在后文。
- 未复现用户电脑上的具体安全弹窗，未在真实安装包中测试安装、卸载和默认应用；未测量性能指标，也未核实独立仓库的重格式插件发布情况。

## 必须优先整改的问题

### R1：文档链接允许脚本 URL，且未配置 CSP（P1）

位置：`app/ui/render-dom.js:12`、`app/tauri.conf.json:10`、`plugins/markdown/src/lib.rs:173`。

Markdown 的链接地址被直接传入 IR，渲染器原样赋给 `a.href`。探针确认 `javascript:window.__TAURI__.core.invoke(...)` 被保留；页面启用了全局 Tauri，CSP 为 null。恶意文档在用户点击链接后，存在以应用页面身份执行脚本并访问原生命令的风险。

本轮确认的是不安全地址未被过滤，以及相关配置；未在真实 WebView 中执行攻击链。

整改：对链接解析后执行明确的协议白名单，拒绝脚本 URL、非法地址及不受支持的协议。外部网页交给系统浏览器，本地链接走受控导航。配置 CSP，限制导航和原生命令权限，不能仅靠 CSP 替代地址校验。

验收：恶意链接不能执行脚本或调用 IPC；正常网页与受支持的本地链接仍可用；加入真实 WebView 回归用例。

### R2：切换文件和退出时没有未保存保护（P1）

位置：`app/ui/main.js:21`、`app/ui/main.js:115`。

前端没有 dirty 状态，也没有离开文档或关闭窗口的保存决策。编辑 A 后打开 B 会隐藏旧编辑器并切换 handle；再次编辑时旧草稿被新快照覆盖。探针已复现该切换路径。

整改：维护当前文档、草稿、编辑基线和 dirty 状态；所有切换来源统一经过「保存 / 放弃 / 取消」。保存失败或用户取消时继续保留当前文档和草稿。关闭窗口也走同一流程。

验收：按钮、目录树、拖放、文件关联和关闭窗口都不能静默丢弃未保存内容。

### R3：ZIP 内成员保存成功，却没有更新原 ZIP（P1）

位置：`crates/vw-core/src/session.rs:151`、`crates/vw-core/src/session.rs:98`、`app/src/lib.rs:51`。

成员物化为临时文件后重新打开，获得文本插件的编辑能力；保存管线写入 `OpenedDoc.path`，该路径指向物化文件，而非原 ZIP。

实际探针结果：`editable=true`；保存返回 23 字节成功；物化文件变为 `modified archive member`；原 ZIP 字节完全未变。这会让用户误以为归档已经保存。

整改：本轮桌面交付建议将归档成员设为只读，或提供明确的「导出 / 另存为」。如果后续支持归档内编辑，需要独立的归档写回契约、外层冲突检测、原子替换和嵌套归档决策，不能沿用临时文件保存后宣称完成。

验收：当前版本不能对仅修改临时文件的操作显示「已保存原归档」；只读限制应在核心执行，覆盖 GUI/CLI/MCP。

### R4：保存后快照、预览和搜索仍使用旧内容（P1）

位置：`plugins/text/src/logic.rs:76`、`plugins/text/src/logic.rs:80`、`crates/vw-core/src/session.rs:98`、`app/ui/main.js:125`。

插件序列化只生成新字节；核心写盘后只更新保存基线，没有刷新打开的插件文档。GUI 保存后仍用同一 handle 拉页，因此拿到旧块。再次进入编辑器也会取回旧快照，后续保存可能覆盖此前修改。

文本探针输出：序列化结果为 `changed\n`，随后 snapshot 和 blocks 仍为 `original\n`。ZIP 成员实际保存探针同样显示：物化文件改变后，snapshot 仍为 `inside zip`。JSON、Markdown、CSV 也采用缓存模型，需要一并核查。

整改：定义保存成功后的文档刷新契约，重新打开或重建插件文档并原子替换句柄，更新元数据、预览、搜索、大纲和编辑快照。刷新失败必须明确区分「磁盘已保存」与「显示未刷新」，保留用户草稿；不能只在 DOM 上改文字。

验收：连续编辑保存两次，第二次基于第一次的内容；保存后预览、搜索和大纲与磁盘一致。

### R5：失败打开后仍保留旧文档的操作状态（P1）

位置：`app/ui/main.js:39`、`app/ui/main.js:125`。

失败分支只替换内容区域，没有协调 handle、编辑状态、按钮和路径栏。探针在成功打开 B、再打开不存在的路径后调用保存，保存命令仍发送给 B 的 handle。真实操作是否可触发还取决于当时按钮状态，但旧文档与新路径不一致已经确认。

整改：将路径输入草稿与当前文档真实路径分开；打开成功后一次性提交文档状态，打开失败时保持完整旧文档或进入完整错误状态，不能混用。保存始终展示真实目标。

验收：打开失败后，标题、路径、按钮和保存目标一致，不出现错误路径下保存旧文档的情况。

## 设计层面的调整

现有内核与插件边界值得保留：目录识别与查看已经实现；GUI 不需要重写文本、JSON 或归档解析。新增目录树可在外壳维护展开状态，通过目录插件读取各层内容。若表格 IR 无法稳定标识成员，补充结构化成员身份，不应依赖第一列文字或 badge 展示文本。

GUI「薄壳」不代表没有产品状态。建议集中维护 currentDoc、workspaceRoot、navigation、draft、dirty、requestGeneration，并将所有打开入口交给同一控制器。文件关联、原生菜单和拖放只提交打开请求，不能各自复制一套打开与状态重置逻辑。

发布也需要成为明确交付阶段：开发 EXE、便携版和安装版是不同产物。安装版要考虑数据目录、WebView2 运行时、文件关联、升级和卸载；便携版要考虑相邻目录可写性及可选注册。签名必须发生在最终产物上，并记录验证结果。

## 分阶段整改计划

### 阶段 A：修复安全和数据语义

处理 R1–R5，补充保存后刷新与归档成员只读契约；统一文档切换和未保存决策。先形成可信的「打开 → 编辑 → 保存 → 再次编辑」流程。

验收：恶意链接不能执行；未保存内容不静默丢失；连续两次保存正确；失败打开不混用状态；归档成员不会假装写回原 ZIP。

### 阶段 B：完成桌面浏览体验

增加原生文件/文件夹选择器、快捷键、拖放、目录树、返回上级与刷新、文档大纲；修复 R6–R11；关闭旧文档并控制并发。将错误状态、加载状态和空状态作为正式界面的一部分。

验收：普通用户无须手输路径即可浏览文件夹、打开和编辑文件；大纲与搜索跳转正确；所有入口遵守同一草稿保护规则。

### 阶段 C：完成 Windows 系统集成与发布

配置 GUI 子系统及 sidecar 隐藏控制台；接入启动参数和重复打开路由；生成安装版及便携版；注册支持的格式与「打开方式」；处理数据目录、WebView2 依赖、卸载与升级；签署正式 EXE 和安装包。

验收：在干净 Windows 标准用户环境完成下载、安装、双击启动、文件关联、再次打开、升级和卸载。用含空格、中文的文件路径测试参数引用。不强制改写用户默认程序。

### 阶段 D：完成格式与性能验收

实现受控 blob 通道；明确本版本实际支持的格式及可编辑范围；按需接入重格式插件；测量大文件首屏、内存和响应；调整耗时命令执行方式；用证据更新设计完成状态。

验收：能力矩阵中每个「已交付」项目都有可运行产物、真实用户流程和验收记录。尚未实现的功能明确标为暂缓。
